# Process log

What was decided, what went wrong, and what each mistake changed. Newest at the bottom. The point of keeping this next to the results is that a clean history would hide the part of the work that matters most: the checks.

## 2026-09-30

**Scope.** The model predicts the direction of a 15-minute window from public exchange data only. Trading venues and contract prices are deliberately out of scope; this repo is about the prediction problem.

**Baselines before models.** The first thing built was the lead-only logistic regression, because any model that cannot beat it has learned nothing the current price does not show. Most of the later studies are read against it.

**Bug: hand-typed number.** The first README draft carried an AUC of 0.526 for the boundary check; the generated table said 0.525. `scripts/update_readme.py` was written so that tables are spliced from `results/` and never typed.

**Lesson from a prototype: score on the label you mean.** A prototype that preceded this repo scored trades on the candle outcome instead of the settlement it was meant to model, and showed a +5c edge that vanished when scored on the right outcome. Carried in: the label is defined once, in `features.py`, and every study reads it from there.

**Decision: the forward log is append-only.** `log.py` freezes models trained through a cutoff month and scores each later window once. `merge_log` never changes an existing row; three tests cover it. The first forward month (September) came out at 50.4% at the open against 53% in the backtest, and the docs say so.

**Decision: day-clustered uncertainty everywhere.** Windows in one day share conditions. All intervals resample whole days and the permutation test shuffles labels within days; `tests/test_stats.py` checks that a model which only knows each day's drift gets no credit.

**Bug: triple-barrier leak at minute 3.** The first meta-labelling run showed 74% at minute 3 for fixed 10 bp barriers, up from 66%. Barriers measured from the open could be touched in minutes 1 to 3, which the model already sees at minute 3. Fixed so barriers apply from the entry price over the remaining minutes. Regression test: a window with a 30 bp spike at minute 1 must be labelled by the spike at minute 0 and not at minute 3. Corrected result: the direction of the remaining path at minute 3 is a coin flip (51%).

**Bug: feature cache collision.** To cut CPU load, features were cached to disk keyed on the series time span. Four coins over the same months share a span, so ETH, SOL and DOGE silently read BTC's file and the multi-asset table showed four identical rows. The key now includes a hash of the prices and volumes; the test builds two series on the same timestamps and asserts they get different files and different features.

**Decision: GPU for XGBoost and the GRU, host threads capped at two.** XGBoost on the GPU still used every CPU core for host-side work. With the cap an XGBoost fit averages 0.84 cores. The random forest has no GPU path and stays capped. `scripts/run_queue.py` starts jobs only when fewer than two of this repo's own jobs are running, so browser and remote-desktop load in the background do not block the queue.

**Result that changed the plan.** Honest nested tuning came out only 0.04 points below tuning on the test month. With 30 trials and a small space on a weak signal there is little to overfit; the gap that notebooks usually hide grows with trials and flexibility. Worth repeating with a larger search to show the effect.

**Ensembles found nothing to combine.** Averaging four base models equals the best single one at the open; the honest stacker is slightly behind. A test spies on the stacker's fits and asserts each one sees only the rows before the month it scores (600 rows for the first stacked month, 1,200 for the next), which is the check that makes the "slightly behind" believable.

**Database write path.** `publish.py` upserts one document per (model, window, minute) and uses `$setOnInsert` for the probability, so a re-send can never change a logged value; only the outcome field may be filled in later. The daily runner publishes when `MONGODB_URI` is set and says so when it is not. The CSV in git stays the audit record; the database is the serving copy, and the run prints a mismatch if the two counts differ.

**Four diagnostics from one set of predictions.** Calibration, conformal abstention, adversarial validation and importance-over-time all read the same walk-forward probabilities, so they were written as one module with the statistics as pure functions and the runner underneath. The tests check the Brier decomposition identity, that recalibration halves a planted error, that conformal coverage meets its target and abstains more as the target rises, and that permutation importance is zero for a feature the model never used.

**Adversarial validation reframed the drift question.** The months are easy to tell apart (AUC up to 0.84) but only by their volatility level, while the direction accuracy does not decay. Inputs drift; the relationship does not. That is a specific reason to keep every feature scale-free.

**The event library was the owner's question**, "can we predict from markers like a price breaking a level", and it was worth asking twice: the first, hand-picked version (a few level types on raw candles) found nothing, while the systematic version with forty conditions, a false-discovery correction and a month-by-month stability check found a consistent reversal structure at the open. The lesson recorded here is that a null from a handful of hand-picked rules is weak evidence; the answer came from testing many rules with the correction that many rules require.

**The September puzzle got a second reading.** The frozen forest scored 50.4% at the open in September; the event rules, found on data through August, held in 27 of 29 cases and a parameter-free rule scored 52.5% on the same windows. Recorded as: signal probably intact, model probably unstable, one more month decides. A simpler rule generalising where a fitted model did not is the kind of result worth keeping in view when the next model is chosen.

**The quiet gate learned which jobs need the GPU.** The pattern study is CPU-only but was refused for an hour because another program held the GPU at 90%. `run_queue.py --cpu-only` skips the GPU checks; the memory and idle-CPU checks still apply.

**Mined rules are the event library, sharpened.** Reading a forest leaf by leaf produced 248 stable rules, the strongest at 35% and 61.5% up on 3% of windows each, against 38% and 57% for the best single events. They combine two or three signs of the same reversal. Path-shape clustering added nothing beyond the indicators.

**"Put the good bits in one model" was tested the honest way and lost.** The rule-ensemble model, with rules mined and weights fit on earlier months only, scored 52.7% at the open against the forest's 53.4%. A model built from a forest's leaves cannot know more than the forest. The wider event search (1,506 candidates) produced 779 "stable" survivors, which was read as a symptom: one effect, hundreds of overlapping descriptions. Both are in the report so that the next person does not repeat them.

**Bug: the 5-minute metrics described the future.** The first derivatives run showed 65% at the open (from 53%) and 66% in September. Too good to be true, and it was: Binance's metrics row stamped T covers the five minutes starting at T, and the carry-forward treated it as known at T, so the model saw the first five minutes of the window it was predicting. Caught by two checks: permutation importance put all 14 points on one feature (the taker buy/sell ratio), and that feature correlated +0.26 with the next five minutes against +0.10 with the previous five. Fixed by delaying every metrics row by 300 seconds (correlation with the next 15 minutes now -0.01), with a regression test. The wrong table was never written up; the cached features built from it were deleted. Lesson recorded in the fix plan: any external series needs a "when is this row known" check before it is used, and the cache key must include the content of extra arrays (it did not; that bug was already on the list).

**Council review (three seats).** Verdict: proceed with changes and narrow the claims. The ordered fix plan lives with the project notes; Section 1 (bugs) is next.

## 2026-10-01

Section 1 of the review's fix plan: fifteen named bugs, each fixed with a regression test that fails on the old code, then every table regenerated by its script. Entries below say what was wrong and what changed; the regenerated tables carry the numbers.

**Volatility deciles were cut on the frame being scored.** `rules.events` took the 10th and 90th percentiles of `vol60` from whatever rows it was given, so the rule-ensemble model and the event portfolio defined "high volatility" on the test month itself. The cutoffs now come from the first three months (training-only in every walk-forward) or from the caller's training rows, and the forward check reuses the training cutoffs.

**The large-trade threshold saw the future.** A trade counted as large if it was in the top 1% of its whole month, so a window on the 3rd used trade sizes from the 30th. The threshold is now the previous UTC day's 99th percentile; each month stores its daily cutoffs so the next month's first day can use them. All tick files were rebuilt.

**Weekday started on Sunday.** `(t // 86400 + 4) % 7` maps 1970-01-01 (a Thursday) to 4, which makes Sunday 0 and turned "weekend" (`wday >= 5`) into Friday and Saturday. Now Monday is 0. The feature version moved to 3, which invalidates every cached feature file.

**The last window was dropped, and features were conditioned on the future.** `window_starts` stopped one window early. `features()` returned nothing when any candle in the predicted window was missing, which is a condition on the future (harmless for the historical tables, since the label needs those candles anyway, but wrong for live use). Features now depend only on candles before minute k; whether the label exists is a separate check in `dataset()`.

**The cache key ignored most of what a dataset depends on.** It hashed close and volume every 997th row. It now covers all seven columns, the ok mask, the contents of every extra array, the tick table, the window constants, the feature version and a hash of the indicator code.

**Funding froze for the forward month.** Only August's funding file was loaded for September, so funding sat at August's last value. Binance publishes funding only as monthly files (checked 2026-10-01: no daily files, and September's monthly file is not out yet). The build now loads the month of every day it covers, marks funding unknown once the last settlement is more than nine hours old, and the forward check leaves out any derivative column that is not known for the whole forward period, naming it in the table. The open-interest timestamp conversion no longer depends on the datetime resolution pandas picks.

**Stability was judged against a direction the scored months helped set.** "Stable in six of eight months" compared each month with the pooled direction over all months. Events are now stable when the direction they had in the three reference months holds in three quarters of the later months; mined rules and shapes are compared with the direction they had on the mining half. Writing the test exposed a separate bug: `day_pvalue` returned 1 when an event deviated by the same amount every day (zero spread made the standard error zero). It now returns 0 in that case.

**Conformal sets could be empty and were not reported.** Below a 50% target the threshold falls under 0.5 and some sets contain neither class. The table now counts empty, single and two-class sets, coverage counts an empty set as a miss, and targets of 50% and 40% were added so the empty sets are visible.

**The Brier decomposition was binned but presented as exact.** With equal-width bins and every probability between 0.4 and 0.6 at the open, most bins were empty. Bins are now quantiles of the predicted probability, and the table reports the residual the binned decomposition does not explain.

**Barrier labels looked only at closes.** A barrier crossed inside a minute and reversed before the close was missed. Minute highs and lows now decide touches; a minute that crosses both is labelled by its close and counted as ambiguous. Renamed "minute-bar barrier" because one-minute bars cannot order touches inside a minute.

**The purged CV embargo was shorter than the feature lookback.** Four hours against a 24-hour volume baseline meant training windows shared feature history with test windows. The embargo is now the full history length.

**The retrain-age table compared different months.** Age 0 was scored on every month and age 3 only on the last few, so staleness was confounded with which months were scored. Every age is now scored on the same target-month windows, with paired differences against the fresh model.

**The magnitude label at minute 3 included the move already seen.** It measured the move from the open, so the lead (a feature) partly decided it. Now measured from the entry price over the remaining minutes, like the barrier labels.

**Permutation p-values sat at their floor and were attached to the wrong model.** At 500 permutations the smallest possible p is about 0.002, which the table printed as if exact, and the report attached a p computed for XGBoost to the forest. The test now runs 2,000 permutations for every model, each p sits on its own model's row, and a p at the floor prints as "below" the floor. The test itself is replaced in Section 3.

**The forward log was append-only by convention only.** The file was rewritten on every run and saved models were reused whenever the training end month matched. Now a manifest records what the frozen models are (training months, a SHA-256 of each candle file, feature version, indicator code hash, parameters, commit), models are reused only when it matches, new rows are appended without rewriting the file, and every row carries a hash chain that `python -m models.btc_15m.log --verify` checks. Rows logged before this change are chained in place with model_id `pre-manifest`. Because the feature version changed, the frozen models are retrained under the corrected code before the October forward period begins.

**Decision: September is scored again, beside the old rows, never over them.** The bug fixes changed the features (weekday coding above all), so the frozen models had to be re-fitted on the same training months under the corrected code. That raised the question of what to do with September, which the old models had already scored. Overwriting was ruled out: the log's value is that a written row never changes, and the hash chain added the same day would flag the edit. Instead the log is keyed by window, minute and model id, the re-fitted models score September as new rows, and every reader (the README block, the chart, the database publish) shows one model version at a time. September is reported as an out-of-time holdout, since the log was first written after the month had passed; the forward log proper begins with October 2026, with one model and no revisions.

**The 2025 holdout was run a second time, with one row added.** The first run (04:28 UTC) scored the two frozen forward models. The frozen minute-0 model uses price and flow features, and the regenerated ablation shows that model's increment over the one-bit rule was already near zero in the backtest; the model the ablation credits with about a point is the forest with the indicator bank. Scoring the holdout without that model would have answered a question nobody was asking. So the script gained one pre-specified row, a forest on price, flow and indicators fit once on the training months, and was run again with `--force` at the time stamped in the table. Nothing else changed; the first run's numbers for the frozen models are reproduced by the second. The rule stays: the holdout is not re-run to improve a number, and any future re-run is declared here with its reason.

**Every table regenerated, and the headline changed.** With the one-feature baselines in place, the forest's increment over "call the opposite of the previous window" is +0.44 points at the open with intervals across zero on day blocks and month blocks; the best fitted model is +0.69, +0.52 after the correction for having picked it. The reversal itself is 52.2% and holds at all fifteen grid positions, on Coinbase and Bitstamp, under VWAP labels, in 2025 and in September 2026. The report was retitled around the reversal, the README summary is now built by `scripts/headline.py` from the result tables rather than typed, and these claims were withdrawn: "signal intact, model unstable", "a rule with no fitted parameters", "four times the data", "strongest baseline at each minute", "order flow adds about a quarter point", and "0.55 means about 55%" (the calibration slope at the open is 0.63). XGBoost fits differ slightly between the GPU and the CPU, so a model's accuracy can differ by a few hundredths of a point between tables generated on different devices; the walk-forward table is the reference.

**Every minute as a decision time, nine years, six horizons.** The owner's question after the review: forget the window verdict, ask "if this pattern, then which way for the next N minutes", over years, with the changes over time measured rather than assumed. A vectorised feature builder (tested row for row against the per-window one) made 4.5 million decision minutes tractable; the conditional cells, their rotated-label null per year, the era view and the selection-span test are `horizons.py` and `horizons_spans.py`, written up in `docs/horizons.md`. Findings: the reversal has existed since 2018 and is fading; reversals from 4-hour extremes and RSI extremes are 57 to 59% over 3 to 30 minutes in every year; one-minute direction is the hardest horizon; sign is stable across years, size shrinks. Owed: the VWAP-label check for these cells, regimes, and magnitude.

**Regimes: bull and bear leave no fingerprint at the minute scale; volatility does.** The owner asked when the bull and bear markets were and what distinguishes them beyond direction, and whether that was overcomplicating a simple thing. It was not, but the answer is simpler than the question: dated bull and bear phases have nearly identical minute-level microstructure (volatility, peak hour, tails, the reversal rule), the states a walk-forward HMM finds on daily data are volatility states with flat mean returns, and the strong conditional cells are about twice as large in the high-volatility state as in the low one with the same sign. The dating used the Lunde-Timmermann thresholds (sources logged); the HMM runs forward only, with a local forward filter tested against hmmlearn's posterior at the final step, so no state uses a later day.

**HMMs in both roles.** The owner asked whether hidden Markov models should be tried as predictors as well as regime detectors ("all 3": detector, minute-scale predictor, switching baseline). As a detector the states are volatility states and the cells scale with them. As predictors they lose to the one-feature baselines by two to ten points and to `vol60` on the magnitude label, for the reason the literature gives: HMMs on returns find volatility regimes, and three discrete states are a coarse version of the continuous volatility feature already in the model. Recorded as study 29 so the question is not reopened without new evidence.

**The price-action library.** The owner kept seeing "momentum failed at X" and "it's rejecting X" in trading chats and asked whether that vocabulary could help. 79 phrases were written as events that read only earlier candles (so "failed at X" is defined before the fact, not after) and scored with the horizons machinery across nine years. The result is one effect: every phrase that holds describes a probe of an extreme that came back, and the continuation phrases (VWAP reclaim, retest of a broken level, confirmed breakout, lower highs) run backwards at 1 to 30 minutes. Time of day, round numbers, engulfing candles, absorption and squeezes carry no direction. The literature that framed it (Osler's order clustering, Lo-Mamaysky-Wang's mechanical patterns, Sullivan-Timmermann-White on snooping) is logged.

**Inside the window.** The owner's observation that a pattern can say "buy now" without saying "the window closes up" is correct and the table shows why: mid-window patterns fire because the price already moved, so the close label is the lead in disguise while the next-5-minute label carries the bounce. The two agree less than half the time for sharp moves after minute 4. The product implication was adopted: the live view shows short-horizon probabilities per pattern beside the contract level, and the window call separately.
