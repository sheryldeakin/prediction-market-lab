# Process log

What was decided, what went wrong, and what each mistake changed. Newest entries are at the bottom. The log sits next to the results because a clean history would hide the checks.

## 2026-09-30

**Scope.** The model predicts the direction of a 15-minute window from public exchange data only. Trading venues and contract prices are deliberately out of scope; this repo is about the prediction problem.

**Baselines before models.** The first thing built was the lead-only logistic regression, because any model that cannot beat it has learned nothing the current price does not show. Most of the later studies are read against it.

**Bug: hand-typed number.** The first README draft carried an AUC of 0.526 for the boundary check; the generated table said 0.525. `scripts/update_readme.py` was written so that tables are spliced from `results/` and never typed.

**Score on the label you mean (from a prototype).** A prototype that preceded this repo scored trades on the candle outcome instead of the settlement it was meant to model. It showed a +5c edge that vanished when scored on the right outcome. The label is now defined once, in `features.py`, and every study reads it from there.

**Decision: the forward log is append-only.** `log.py` freezes models trained through a cutoff month and scores each later window once. `merge_log` never changes an existing row; three tests cover it. The first forward month (September) came out at 50.4% at the open against 53% in the backtest, and the docs say so.

**Decision: day-clustered uncertainty everywhere.** Windows in one day share conditions. All intervals resample whole days and the permutation test shuffles labels within days; `tests/test_stats.py` checks that a model which only knows each day's drift gets no credit.

**Bug: triple-barrier leak at minute 3.** The first meta-labelling run showed 74% at minute 3 for fixed 10 bp barriers, up from 66%. Barriers measured from the open could be touched in minutes 1 to 3, which the model already sees at minute 3. Fixed so barriers apply from the entry price over the remaining minutes. Regression test: a window with a 30 bp spike at minute 1 must be labelled by the spike at minute 0 and not at minute 3. Corrected result: the direction of the remaining path at minute 3 is a coin flip (51%).

**Bug: feature cache collision.** To cut CPU load, features were cached to disk keyed on the series time span. Four coins over the same months share a span, so ETH, SOL and DOGE silently read BTC's file and the multi-asset table showed four identical rows. The key now includes a hash of the prices and volumes; the test builds two series on the same timestamps and asserts they get different files and different features.

**Decision: GPU for XGBoost and the GRU, host threads capped at two.** XGBoost on the GPU still used every CPU core for host-side work. With the cap an XGBoost fit averages 0.84 cores. The random forest has no GPU path and stays capped. `scripts/run_queue.py` starts jobs only when fewer than two of this repo's own jobs are running. Browser and remote-desktop load in the background therefore do not block the queue.

**Nested tuning against tuning on the test month.** Honest nested tuning scored only 0.04 points below tuning on the test month. With 30 trials, a small space and a weak signal, there is little to overfit. The gap that notebooks usually hide grows with trials and flexibility. Repeating with a larger search would show the effect.

**Ensembles found nothing to combine.** Averaging four base models equals the best single one at the open; the honest stacker is slightly behind. A test spies on the stacker's fits and asserts each one sees only the rows before the month it scores (600 rows for the first stacked month, 1,200 for the next). That check makes "slightly behind" credible.

**Database write path.** `publish.py` upserts one document per (model, window, minute) and uses `$setOnInsert` for the probability, so a re-send can never change a logged value; only the outcome field may be filled in later. The daily runner publishes when `MONGODB_URI` is set and says so when it is not. The CSV in git stays the audit record; the database is the serving copy, and the run prints a mismatch if the two counts differ.

**Four diagnostics from one set of predictions.** Calibration, conformal abstention, adversarial validation and importance-over-time all read the same walk-forward probabilities. They were written as one module: the statistics are pure functions and the runner sits underneath. The tests check the Brier decomposition identity and that recalibration halves a planted error. They also check that conformal coverage meets its target and abstains more as the target rises, and that permutation importance is zero for a feature the model never used.

**Adversarial validation reframed the drift question.** The months are easy to tell apart (AUC up to 0.84), but only by their volatility level, and the direction accuracy does not decay. The inputs drift while the relationship between inputs and direction stays put, so every feature is kept scale-free.

**The event library.** The owner asked, "can we predict from markers like a price breaking a level". The first version, a few hand-picked level types on raw candles, found nothing. The systematic version, with forty conditions, a false-discovery correction and a month-by-month stability check, found a consistent reversal structure at the open. A null from a handful of hand-picked rules is weak evidence; the answer came from testing many rules and applying the correction that many rules require.

**The September result, read against the event rules.** The frozen forest scored 50.4% at the open in September. The event rules, found on data through August, held in 27 of 29 cases, and a parameter-free rule scored 52.5% on the same windows. The reading recorded then was: signal probably intact, model probably unstable, one more month decides. A simpler rule that generalises where a fitted model does not should stay in view when the next model is chosen.

**The queue's quiet profile skips GPU checks for CPU-only jobs.** The pattern study is CPU-only. It was refused for an hour because another program held the GPU at 90%. `run_queue.py --cpu-only` skips the GPU checks. The memory and idle-CPU checks still apply.

**Mined rules combine signs from the event library.** Reading a forest leaf by leaf produced 248 stable rules. The strongest were 35% and 61.5% up on 3% of windows each, against 38% and 57% for the best single events. Each rule combines two or three signs of the same reversal. Path-shape clustering added nothing beyond the indicators.

**Combining the good rules in one model was tested and lost.** The rule-ensemble model, with rules mined and weights fit on earlier months only, scored 52.7% at the open against the forest's 53.4%. A model built from a forest's leaves cannot know more than the forest. The wider event search (1,506 candidates) produced 779 "stable" survivors, which was read as a symptom: one effect described hundreds of times by overlapping rules. Both results are in the report so that the next person does not repeat them.

**Bug: the 5-minute metrics described the future.** The first derivatives run showed 65% at the open (from 53%) and 66% in September, which was implausibly high. A row of Binance's metrics stamped T covers the five minutes starting at T. The carry-forward treated it as known at T, so the model saw the first five minutes of the window it was predicting. Two checks caught it. Permutation importance put all 14 points on one feature (the taker buy/sell ratio), and that feature correlated +0.26 with the next five minutes against +0.10 with the previous five. The fix delays every metrics row by 300 seconds (correlation with the next 15 minutes is now -0.01) and has a regression test. The wrong table was never written up, and the cached features built from it were deleted. The fix plan records two rules. Every external series needs a "when is this row known" check before use. The cache key must include the content of extra arrays (it did not; that bug was already on the list).

**Outside review (three reviewers).** Verdict: proceed with changes and narrow the claims. The ordered fix plan lives with the project notes; Section 1 (bugs) is next.

## 2026-10-01

This section covers Section 1 of the review's fix plan. It lists fifteen named bugs, each fixed with a regression test that fails on the old code, and every table was then regenerated by its script. Entries below say what was wrong and what changed; the regenerated tables carry the numbers.

**Volatility deciles were cut on the frame being scored.** `rules.events` took the 10th and 90th percentiles of `vol60` from whatever rows it was given. The rule-ensemble model and the event portfolio therefore defined "high volatility" on the test month itself. The cutoffs now come from the first three months (training-only in every walk-forward) or from the caller's training rows. The forward check reuses the training cutoffs.

**The large-trade threshold saw the future.** A trade counted as large if it was in the top 1% of its whole month, so a window on the 3rd used trade sizes from the 30th. The threshold is now the previous UTC day's 99th percentile; each month stores its daily cutoffs so the next month's first day can use them. All tick files were rebuilt.

**Weekday started on Sunday.** `(t // 86400 + 4) % 7` maps 1970-01-01 (a Thursday) to 4, which makes Sunday 0 and turned "weekend" (`wday >= 5`) into Friday and Saturday. Now Monday is 0. The feature version moved to 3, which invalidates every cached feature file.

**The last window was dropped, and features were conditioned on the future.** `window_starts` stopped one window early. `features()` returned nothing when any candle in the predicted window was missing. That conditions on the future: harmless for the historical tables, since the label needs those candles anyway, but wrong for live use. Features now depend only on candles before minute k, and whether the label exists is a separate check in `dataset()`.

**The cache key ignored most of what a dataset depends on.** It hashed close and volume every 997th row. It now covers all seven columns, the ok mask, the contents of every extra array and the tick table. It also covers the window constants, the feature version and a hash of the indicator code.

**Funding froze for the forward month.** Only August's funding file was loaded for September, so funding sat at August's last value. Binance publishes funding only as monthly files (checked 2026-10-01: no daily files, and September's monthly file is not out yet). The build now loads the month of every day it covers and marks funding unknown once the last settlement is more than nine hours old. The forward check leaves out any derivative column that is not known for the whole forward period, and names it in the table. The open-interest timestamp conversion no longer depends on the datetime resolution pandas picks.

**Stability was judged against a direction the scored months helped set.** "Stable in six of eight months" compared each month with the pooled direction over all months. Events are now stable when the direction they had in the three reference months holds in three quarters of the later months. Mined rules and shapes are compared with the direction they had on the mining half. Writing the test exposed a separate bug: `day_pvalue` returned 1 when an event deviated by the same amount every day (zero spread made the standard error zero). It now returns 0 in that case.

**Conformal sets could be empty and were not reported.** Below a 50% target the threshold falls under 0.5 and some sets contain neither class. The table now counts empty, single and two-class sets, and coverage counts an empty set as a miss. Targets of 50% and 40% were added so the empty sets are visible.

**The Brier decomposition was binned but presented as exact.** With equal-width bins and every probability between 0.4 and 0.6 at the open, most bins were empty. Bins are now quantiles of the predicted probability, and the table reports the residual the binned decomposition does not explain.

**Barrier labels looked only at closes.** A barrier crossed inside a minute and reversed before the close was missed. Minute highs and lows now decide touches; a minute that crosses both is labelled by its close and counted as ambiguous. Renamed "minute-bar barrier" because one-minute bars cannot order touches inside a minute.

**The purged CV embargo was shorter than the feature lookback.** Four hours against a 24-hour volume baseline meant training windows shared feature history with test windows. The embargo is now the full history length.

**The retrain-age table compared different months.** Age 0 was scored on every month and age 3 only on the last few, so staleness was confounded with which months were scored. Every age is now scored on the same target-month windows, with paired differences against the fresh model.

**The magnitude label at minute 3 included the move already seen.** It measured the move from the open, so the lead (a feature) partly decided it. Now measured from the entry price over the remaining minutes, like the barrier labels.

**Permutation p-values sat at their floor and were attached to the wrong model.** At 500 permutations the smallest possible p is about 0.002, which the table printed as if exact. The report also attached a p computed for XGBoost to the forest. The test now runs 2,000 permutations for every model, and each p sits on its own model's row. A p at the floor prints as "below" the floor. The test itself is replaced in Section 3.

**The forward log was append-only by convention only.** The file was rewritten on every run and saved models were reused whenever the training end month matched. Now a manifest records what the frozen models are (training months, a SHA-256 of each candle file, feature version, indicator code hash, parameters, commit). Models are reused only when it matches. New rows are appended without rewriting the file, and every row carries a hash chain that `python -m models.btc_15m.log --verify` checks. Rows logged before this change are chained in place with model_id `pre-manifest`. Because the feature version changed, the frozen models are retrained under the corrected code before the October forward period begins.

**Decision: September is scored again, beside the old rows, never over them.** The bug fixes changed the features (weekday coding above all), so the frozen models had to be re-fitted on the same training months under the corrected code. That raised the question of what to do with September, which the old models had already scored. Overwriting was ruled out. The log's value is that a written row never changes, and the hash chain added the same day would flag the edit. Instead the log is keyed by window, minute and model id, and the re-fitted models score September as new rows. Every reader (the README block, the chart, the database publish) shows one model version at a time. September is reported as an out-of-time holdout, since the log was first written after the month had passed. The forward log proper begins with October 2026, with one model and no revisions.

**The 2025 holdout was run a second time, with one row added.** The first run (04:28 UTC) scored the two frozen forward models. The frozen minute-0 model uses price and flow features. The regenerated ablation shows that its increment over the one-bit rule (the opposite of the previous window's direction) was already near zero in the backtest. The model the ablation credits with about a point is the forest with the indicator bank. Scoring the holdout without that model would have answered a question nobody was asking, so the script gained one pre-specified row: a forest on price, flow and indicators, fit once on the training months. It was run again with `--force` at the time stamped in the table. Nothing else changed, and the second run reproduces the first run's numbers for the frozen models. The rule stays: the holdout is not re-run to improve a number, and any future re-run is declared here with its reason.

**Every table regenerated, and the headline changed.** With the one-feature baselines in place, the forest's increment over the one-bit rule is +0.44 points at the open, with intervals across zero on day blocks and month blocks. The best fitted model is +0.69, or +0.52 after the correction for having picked it. The reversal itself is 52.2% and holds at all fifteen grid positions, on Coinbase and Bitstamp, under VWAP labels, in 2025 and in September 2026. The report was retitled around the reversal. The README summary is now built by `scripts/headline.py` from the result tables rather than typed. XGBoost fits differ slightly between the GPU and the CPU, so a model's accuracy can differ by a few hundredths of a point between tables generated on different devices. The walk-forward table is the reference. These claims were withdrawn:

- "signal intact, model unstable"
- "a rule with no fitted parameters"
- "four times the data"
- "strongest baseline at each minute"
- "order flow adds about a quarter point"
- "0.55 means about 55%" (the calibration slope at the open is 0.63)

**Every minute as a decision time, nine years, six horizons.** After the review, the owner asked a different question: if this pattern holds, which way does the price go over the next N minutes? The window verdict was set aside. The question was to be answered across years, measuring changes over time rather than assuming them. A vectorised feature builder (tested row for row against the per-window one) made 4.5 million decision minutes tractable. The code is `horizons.py` and `horizons_spans.py`, written up in `docs/horizons.md`. It computes conditional cells (one table row per pattern and horizon), their rotated-label null per year, the era view and the selection-span test. The reversal has existed since 2018 and is fading. Reversals from 4-hour extremes and RSI extremes are 57 to 59% over 3 to 30 minutes in every year. One-minute direction is the hardest horizon. The sign of the cells is stable across years while their size shrinks. Still owed: the VWAP-label check for these cells, regimes, and magnitude.

**Regimes: bull and bear phases look alike at the minute scale; volatility states differ.** The owner asked when the bull and bear markets were, what distinguishes them beyond direction, and whether that overcomplicated a simple thing. It did not, and the answer is simpler than the question. Dated bull and bear phases have nearly identical minute-level microstructure (volatility, peak hour, tails, the reversal rule). The states a walk-forward HMM finds on daily data are volatility states with flat mean returns. The strong conditional cells are about twice as large in the high-volatility state as in the low one, with the same sign. The dating used the Lunde-Timmermann thresholds (sources logged). The HMM runs forward only, with a local forward filter tested against hmmlearn's posterior at the final step. No state uses a later day.

**HMMs in both roles.** The owner asked whether hidden Markov models should be tried as predictors as well as regime detectors ("all 3": detector, minute-scale predictor, switching baseline). As a detector, the states are volatility states and the cells scale with them. As predictors, they lose to the one-feature baselines by two to ten points and to `vol60` on the magnitude label. The literature gives the reason: HMMs on returns find volatility regimes, and three discrete states are a coarse version of the continuous volatility feature already in the model. This is recorded as study 29 so the question is not reopened without new evidence.

**The price-action library.** The owner kept seeing "momentum failed at X" and "it's rejecting X" in trading chats and asked whether that vocabulary could help. In response, 79 phrases were written as events that read only earlier candles, so "failed at X" is defined before the fact, not after. They were scored with the horizons machinery across nine years. The result is one effect: every phrase that holds describes a probe of an extreme that came back. The continuation phrases (VWAP reclaim, retest of a broken level, confirmed breakout, lower highs) run backwards at 1 to 30 minutes. Time of day, round numbers, engulfing candles, absorption and squeezes carry no direction. The literature that framed it (Osler's order clustering, Lo-Mamaysky-Wang's mechanical patterns, Sullivan-Timmermann-White on snooping) is logged.

**Inside the window.** The owner observed that a pattern can say "buy now" without saying "the window closes up". The table shows this is correct: mid-window patterns fire because the price already moved, so the close label is the lead in disguise, while the next-5-minute label carries the bounce. The two labels agree less than half the time for sharp moves after minute 4. The product decision followed: the live view shows short-horizon probabilities per pattern beside the contract level, and the window call separately.

**HMM round two: states as features, and a model per state.** The owner asked to revisit the HMM predictors "with less simple rules". Three variants went into the forest that already works, walk-forward on the same windows. The first adds the minute-scale state probabilities as columns. The second adds the previous day's regime as a one-hot. The third is a forest per state, mixed by the filtered probabilities. The first two move accuracy by about a tenth of a point, with intervals across zero. The mixture of experts is seven tenths worse, with an interval that excludes zero. This is recorded as study 30, and the HMM line is closed for the window label on returns. The variants that would reopen it (an order-flow observable, time-of-day transitions, explicit durations) are listed in horizons.md so they are tried deliberately or not at all.

**One probability per minute from the cells, and what a trade costs.** This covers refinements 1, 2 and 6 of the owner's refine-before-extend list. A logistic regression on all 186 events plus the volatility tercile, walk-forward by year, beats the previous-h reversal rule (h is the horizon) by about a point at 5 and 15 minutes. The rule "the strongest firing cell decides" matches it, so the live view can show ranked cells rather than a model. The forward calibration check compared promised with delivered (650 and 684 cell-years). It found the sign kept in 99% of cases and about nine tenths of the size delivered, so the cells can be shown as probabilities. A cost sentence went into the magnitude section with the fee schedule logged. A 5 bp bounce is below one side of the spot taker fee, so the window contract is the only instrument, pending real quotes.

**The cells as a few effects.** Refinements 3 to 5. Co-firing under a nesting measure (overlap coefficient) puts 85 of the 107 indicator events into two clusters, "price recently rose" and "price recently fell". The price-action probes fall into small clusters of their own. The first cut used Jaccard, which kept rare events apart from the broad ones they fire inside and produced 108 clusters. Both measures are therefore reported with their cluster counts at three cuts. The horizon table was extended to 60 minutes when the first run showed every top cell still rising at 30. The deviation reaches 77% of its 30-minute size by 5 minutes and peaks at 48 to 60 minutes for the range and wick cells. The trailing-hour volatility tercile does not scale the cells (ratio 1.0), which conflicts with the daily-state doubling in the regime study. The era is the likely common cause and is noted as untested. The regime bullet that pointed at vol60 as the regime variable was corrected in the same commit.

**The regime doubling was the era.** First item of the backlog, two hours as sized. The 24 strongest cells were scored by daily HMM volatility state inside each era. The high-over-low ratio is 1.38 pooled over all years and 0.93 within eras. Of the 189 high-volatility days, 130 fall in 2020 to 2022, and 2019, with four such days, has the largest deviations of all. The regime bullet, the cells-section bullet and the study 29 sentence that read the doubling as a volatility effect were rewritten. The finding now is that the calendar, not volatility or bull and bear, is the regime variable for these cells.

**Outside review, round two (three reviewers, blind), and the owner's decisions.** The reviewers were asked what to pursue next, what to drop, and what had been missed. All three would drop the HMM variants, new model families and the derivatives or tick event libraries. They split on the first step (contract quotes, tick mechanism, or the forward log as primary evidence) and on extending the data. The owner decided that the tracking layer will collect contract quotes beside the forward log, and tabled rather than dropped the HMM, library and data items until the dashboard exists. The repo's decision that no venue enters the model code stands, and quotes live in the tracking layer. Adopted from the review:

- **A compact continuous model against the named events.**
- **A later-entry and month-block check for the top cells.**
- **Fading as a forecast, with a held-out record.**
- **Three reporting fixes.** The cell-year count is not an independence count; the backtest's detectable increment is stated in the README; month blocks sit beside day blocks for the top cells.

**Compact model, later entry, fading forecast.** These are items 1 to 3 from the outside review, run the same evening. A spline logistic regression on nine continuous quantities matches the 186-event cells model within half a point every year, and the sign of the difference changes from year to year. The named events are therefore an interpretation layer, and the compact model is the forecast to freeze. The strongest cells keep 81% of their 5-minute deviation and 93% of their 30-minute deviation when entry is delayed one minute past the shared boundary print. Every month-block interval excludes zero. The fading, fitted as a straight line, is about a point a year for the range and wick cells (zero around 2031 to 2037) and slower for the sharp-move cells. The line is only a fair forecaster (it beats "same as last year" in 9 of 16 cells), so expiry is stated as a range.

## 2026-10-05

**The mechanism study, rule first.** The backlog item on the mechanism of the reversal was run as two pre-specified hypotheses the per-second trade table can see: bid-ask bounce or last-trade noise, against transient price impact. The code, its tests and the decision rule in `docs/horizons.md` were committed before the full run, so the rule cannot have been fitted to the tables. A two-month smoke run of the code came first and changed no definition or threshold (only captions). The events are the six already in the library. Each has one control minute matched on year, hour and previous-year volatility decile. Controls are kept out of the 30 minutes after any firing, so an episode's aftermath is not a control. The verdict by the rule is "unidentified with this data". Every prediction of the bounce reading failed. The embargoed labels keep most of the deviation, and the event minute carries heavy flow. But the recovery does not grow with the flow, so the third condition of the price-impact reading is missing. The study section names quotes and depth around the events as the data that would settle it.

**A shared raw-data directory for second working copies.** `LAB_DATA_ROOT` points the raw-data readers (klines, ticks, futures, venues) at another directory, so a second working copy reads the first one's downloads without copying 7 GB. The feature cache and the study's event frames stay in the working copy's own `data/`. The study refuses to run if a raw file is missing rather than downloading into the shared directory, and a test covers this. A queued run from a second working copy needs the interpreter's absolute path, because `run_queue.py` swaps a bare `python` for the checkout's own `.venv`, which a worktree does not have.

**Hour of day and the calendar.** The forward log shows wide hour-to-hour differences on 132 windows per hour, which is the size noise alone produces, so the question was put to nine years. Five families of slices (hour, weekday, session, month, event slot) were scored against the previous-window reversal at the open, the lead-sign rule at minute 3 and the six strongest any-minute cells. Each slice carries an adjusted p from labels rotated within months, read against its own family, with the nine yearly estimates pooled the way the real ones are. No hour clears for either rule. Saturday is more accurate than the year for the reversal (8 of 9 years, p at the null floor) and recurs in three cells. The lead rule has one borderline session. The study was run once, in 287 seconds, and the event slots are fixed in UTC and ignore daylight saving.

**Derivatives and tick events for the library.** The backlog item was run as eleven tick events and eight derivatives events. The tick events are the large-trade burst and its two sides, three and five minutes of one-sided flow in both directions, and the trade-count climax with and without a price extreme. Definitions and tests were committed before the nine-year run. The derivatives events could not be scored: the futures files held cover less than a calendar year, and every cutoff is a percentile of the previous year, so no year has one. The definitions and their tests stand, a generated coverage table says why, and the item stays on the backlog with the downloads it needs. The tick run showed two things. First, the plain trade-count climax fires on a share of minutes that varies by an order of magnitude or more between years. An absolute count cut at the previous year's 99th percentile measures how much busier the year is than the last one. The two variants at a price extreme are the readable ones. Second, the first summary sentence counted only cells that clear the search-wide null in every year, which gave none, since the early years fire far less and have little power. The sentence now reports three tiers, and the section says that this was decided after seeing the first result. Bug caught while caching: `Path.with_suffix` replaced everything after the last dot of a cache key that contained one (`0.99`), so every year would have written to the same file name. The key no longer contains a dot, and a test asserts this.

**HMM round two, the tabled variants (study 32).** Pre-registered in the study text before the full run: a variant adds something only when its day-block and month-block intervals over the one-feature baseline both lie above zero. Run as written, six variant rows meet it, all at the open, and the forest with no HMM column meets it too. The table therefore carries a column against that forest, which is what attributes a gain, and no variant differs from the forest. The reference row reproduces study 30's base row to the printed digit. This checks that the new walk-forward and the old one score the same windows. Two decisions were made along the way:

- **The window-feature HMM keeps the best of five restarts.** A test on planted clusters showed single EM runs landing in a poor optimum in two of five seeds.
- **The non-homogeneous HMM is time-bucketed, with the emissions held at the homogeneous fit.** Its only difference from the control is then the transition matrices, and the diagnostics line in the table shows they differ.

**The derivatives events, scored.** With the futures history downloaded, the eight derivatives events were run through the library machinery in a separate pass with their own null. The scored years are those whose previous calendar year all three futures series cover in full. The one-year smoke run (2024, 5 null runs) changed one thing before the full run: the comparison at each decile became strict. The funding rate sits at the exchange default on a large share of minutes, and the previous year's upper decile was the default itself. An at-or-above comparison therefore fired on every minute at the default. The regression test plants a mass at the default and asserts that a value at the cut does not fire. It failed on the old comparison before the change. The orientation of the funding and liquidation groups in the effect sentences was fixed before the run. What the run says is in the section's "What it says" bullets. The liquidation signatures reverse the forced move, with the per-year rows tempering it. Open interest rising leans up a little. The funding decile events are a property of the year, as the plain trade-count climax was. A level definition goes on the backlog, beside the question of whether the liquidation signature adds anything to the hard move alone. Two guards came with the wiring. The scoring refuses to download: a missing futures file names itself and stops the run, and a test checks that the download path is never reached. The two library tables come from one renderer, and a test checks that the tick table's text is unchanged.

**Outside review of the derivatives result, and a sign read backwards.** Three independent reviewers (two of them other model families) read the generated table, the section prose and the scoring code blind. They were asked whether the result could stand and what to do next. All three found no lookahead, and all three found the same error: the previous entry's reading "open interest rising leans up a little" was the wrong way round. The rise events lean down at 5 to 30 minutes and the drop events lean up. The bullet had been written from the summary sentence, which listed the rise events among those with a strong cell. That cell was at 1 minute, where the VWAP label keeps a small fraction of it. The reviewers also found three further problems. The share column was the mean of yearly shares over the scored years, while its description said all minutes. The liquidation reading was overstated at the longer horizons: the long signature clears the null in one year there, not two, and its pooled interval is carried by the two busiest years. The strict comparison for funding changed which minutes fire without curing the year-dependence. All three recommended fixing the report before any new study. Taken: the bullets rewritten from the rows, the share column aggregated and labelled, and the tick table regenerated with the same code. Also taken: three generated sentences (events scored in fewer than all years, strong 1-minute cells failing the VWAP check, the per-year range per group). The open-interest groups were split by direction, so a range never merges opposite signs.
